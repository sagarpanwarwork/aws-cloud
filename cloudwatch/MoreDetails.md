## 4. CloudWatch metrics – fundamental concepts

Before creating graphs, understand these terms.

**Metric**

A metric is a time-ordered collection of measurements representing something we want to monitor.

Examples:

- CPU utilization.
- Number of requests.
- Application response time.
- Number of HTTP 5XX errors.
- Number of healthy EC2 targets.

**Namespace**

A namespace is a logical container for related CloudWatch metrics.

Examples:

| Namespace | Purpose |
|---|---|
| `AWS/EC2` | EC2 metrics |
| `AWS/ApplicationELB` | Application Load Balancer metrics |
| `AWS/SQS` | SQS metrics |
| `AWS/Lambda` | Lambda metrics |
| `Academy/EC2` | Custom metrics from our lab |

**Dimension**

A dimension is a name-value pair that identifies a particular metric resource or configuration.

For example:

```text
LoadBalancer = app/za-cw14-alb/1c7acdacae8a94d5
```

A metric can have multiple dimension combinations. The combination must match the dimensions with which AWS published the metric.

**Statistic**

A statistic determines how CloudWatch aggregates metric values over a specified period.

| Statistic | Meaning |
|---|---|
| Sum | Total of all recorded values |
| Average | Mean of recorded values |
| Minimum | Lowest recorded value |
| Maximum | Highest recorded value |
| SampleCount | Number of data samples |

**Period**

The period is the time interval over which CloudWatch aggregates metric data.

For this practical, we use a one-minute period.

For example, if 40 requests are processed during a one-minute period, `RequestCount` with the `Sum` statistic reports 40 for that period.

## 5. Create and visualize ALB metrics

### Step 1 – Open CloudWatch Classic metrics

1. Open AWS Management Console.
2. Navigate to CloudWatch.
3. Confirm the region is Mumbai (`ap-south-1`).
4. Open **Metrics → Classic metrics**.
5. Under Browse, locate the ApplicationELB namespace.

For this practical, use Classic metrics rather than Metrics Explorer. The Classic metrics interface lets us select the exact metric and its dimensions.

### Step 2 – Create the RequestCount graph

Search for:

```text
RequestCount
```

Select:

```text
ApplicationELB → Per AppELB Metrics
```

This metric group contains metrics identified by the load balancer dimension.

Find the row for:

```text
za-cw14-alb
```

Select its `RequestCount` metric.

Open the Graphed metrics tab.

Configure:

| Configuration | Value |
|---|---|
| Metric | RequestCount |
| Statistic | Sum |
| Period | 1 minute |
| Time range | Last 1 hour |

**What does RequestCount measure?**

It measures the number of requests processed by the Application Load Balancer for which a target was selected.

The Sum statistic gives us the total number of requests during the selected period.

### Step 3 – Generate application traffic

Run the following PowerShell command:

```powershell
1..30 | ForEach-Object {
    curl.exe -s -o NUL "$appUrl/"
}
```

This generates 30 successful application requests.

Wait for the next CloudWatch metric publication and refresh the graph.

**Expected observation:** RequestCount increases.

Important: ALB metrics are generally published in 60-second intervals when requests are flowing. Health-check requests are excluded from ALB metrics.

### Step 4 – Create the TargetResponseTime graph

Go back to Browse.

Select:

```text
ApplicationELB → Per AppELB, per TG Metrics
```

Search for:

```text
TargetResponseTime
```

Select the metric associated with the following resources:

```text
LoadBalancer:
app/za-cw14-alb/1c7acdacae8a94d5

TargetGroup:
targetgroup/za-cw14-tg/d25a8ca325b0ad98
```

Open Graphed metrics.

Configure:

| Configuration | Value |
|---|---|
| Metric | TargetResponseTime |
| Statistic | Average |
| Period | 1 minute |

**What does TargetResponseTime measure?**

It measures the time elapsed after the request leaves the load balancer until the target starts sending response headers.

It is a useful application-side response-time signal. It is not the complete client-perceived page load time.

The unit is seconds.

### Step 5 – Understand application-side HTTP 5XX errors

Open Browse again and select:

```text
ApplicationELB → Per AppELB, per TG Metrics
```

Search for:

```text
HTTPCode_Target_5XX_Count
```

Select the metric with the same LoadBalancer and TargetGroup dimensions used in the previous step.

Configure:

| Configuration | Value |
|---|---|
| Metric | HTTPCode_Target_5XX_Count |
| Statistic | Sum |
| Period | 1 minute |

**What does this metric measure?**

It counts HTTP 5XX responses generated by the registered targets, meaning the application or backend targets.

This is different from:

```text
HTTPCode_ELB_5XX_Count
```

`HTTPCode_ELB_5XX_Count` measures HTTP 5XX errors generated by the load balancer itself.

For our practical, we are specifically interested in application-generated errors.

### Step 6 – Generate HTTP 500 errors

Run:

```powershell
1..10 | ForEach-Object {
    curl.exe -s -o NUL -w "%{http_code}`n" "$appUrl/error"
}
```

Expected output:

```text
500
500
500
500
500
500
500
500
500
500
```

Wait for CloudWatch to publish the metric and refresh the graph.

You should see the target 5XX count increase.

## 6. Final CloudWatch graph configuration

We now have three metrics on the same graph.

| Metric | Statistic | Period | Purpose |
|---|---|---|---|
| RequestCount | Sum | 1 minute | Request volume |
| TargetResponseTime | Average | 1 minute | Application response latency |
| HTTPCode_Target_5XX_Count | Sum | 1 minute | Application server errors |

Each metric has its own statistic. Do not accidentally apply `Sum` to every metric.

**Our actual lab observation**

At one recorded one-minute datapoint (09:26 UTC on October 30, 2026), we observed:

| Metric | Recorded value |
|---|---:|
| RequestCount | 40 |
| HTTPCode_Target_5XX_Count | 10 |
| TargetResponseTime | 0.0010854 seconds |

Interpretation:

- 40 requests were processed during that minute.
- 10 responses were application-generated HTTP 5XX errors.
- Average target response time was approximately 1.0854 milliseconds.

These values are observations from our lab, not expected production performance benchmarks.

The 40 requests corresponded to the earlier traffic-generation exercises. Remember that CloudWatch counts all applicable requests reaching the ALB, not only requests from one particular terminal command.

## 7. Create a CloudWatch alarm

Now that we can observe application errors, we will create an alarm.

**Scenario:** We want AWS to notify us whenever the application returns one or more HTTP 5XX responses in a one-minute period.

### Step 1 – Open the alarm creation workflow

In the CloudWatch metric graph:

1. Locate the `HTTPCode_Target_5XX_Count` row.
2. Find the bell icon in the Actions column on that row.
3. Click the bell icon to create an alarm from this metric.

Alternatively, navigate to:

```text
CloudWatch → Alarms → Create alarm
```

Then select the required metric.

### Step 2 – Configure the metric and threshold

Use the following values:

| Setting | Value |
|---|---|
| Metric namespace | AWS/ApplicationELB |
| Metric | HTTPCode_Target_5XX_Count |
| Statistic | Sum |
| Period | 1 minute |
| Threshold type | Static |
| Comparison | Greater than |
| Threshold | 0 |
| Evaluation periods | 1 |
| Datapoints to alarm | 1 out of 1 |
| Missing data | Treat as not breaching |

**Alarm condition:**

```text
HTTPCode_Target_5XX_Count > 0
```

This means that at least one application-generated HTTP 5XX response during the evaluation period will trigger the alarm.

### Step 3 – Configure SNS notification

Under the alarm notification configuration:

1. Select the alarm state trigger: In alarm.
2. Select the existing SNS topic:

```text
academy-class14-alerts
```

3. Confirm that the email subscription for this topic has been confirmed.

An SNS topic distributes published messages to its subscribers. In this lab, the subscriber is an email address.

### Step 4 – Name and create the alarm

Use:

```text
academy-class14-target-5xx
```

Review the configuration and create the alarm.

### Step 5 – Test the alarm

Generate another set of application errors:

```powershell
1..10 | ForEach-Object {
    curl.exe -s -o NUL -w "%{http_code}`n" "$appUrl/error"
}
```

Wait for the metric publication and alarm evaluation.

Expected workflow:

```text
Application returns HTTP 500
          |
          v
ALB records target 5XX metric
          |
          v
CloudWatch receives metric data
          |
          v
CloudWatch evaluates alarm condition
          |
          v
HTTPCode_Target_5XX_Count > 0
          |
          v
Alarm enters ALARM state
          |
          v
SNS publishes notification
          |
          v
Subscribed email receives alert
```

Check the alarm in:

```text
CloudWatch → Alarms
```

The expected state is:

```text
ALARM
```

Also verify that the SNS action is configured and that the email subscription is confirmed. Seeing ALARM proves the threshold was breached; it does not by itself prove that email delivery succeeded.

## 8. Understand CloudWatch alarm states

CloudWatch metric alarms have three primary states.

| State | Meaning |
|---|---|
| OK | The metric does not breach the configured threshold |
| ALARM | The metric breaches the configured threshold |
| INSUFFICIENT_DATA | There is insufficient metric data to determine the state |

For our alarm:

```text
Metric: HTTPCode_Target_5XX_Count
Condition: Greater than 0
Period: 1 minute
```

If the application produces no 5XX responses in a later evaluation period, the alarm should return to OK, assuming the configured evaluation and missing-data behaviour permit it.

## 9. Classroom discussion

Ask students these questions:

**Q1. What is the difference between a metric and an alarm?**

A metric records and exposes measurements. An alarm evaluates a metric against a configured condition and changes state when that condition is met.

**Q2. Why did RequestCount show 40 when we expected fewer requests?**

Because the metric counts applicable requests reaching the ALB during the selected one-minute period. It is not limited to one terminal command or client.

**Q3. Why do we use Sum for RequestCount?**

Because we want the total number of requests processed during the period.

**Q4. Why do we use Average for TargetResponseTime?**

Because we want the mean response time across the recorded samples during the period.

**Q5. What is the difference between HTTPCode_Target_5XX_Count and HTTPCode_ELB_5XX_Count?**

The first measures 5XX responses returned by backend targets. The second measures 5XX responses generated by the ALB.

**Q6. Why do we use SNS with CloudWatch alarms?**

CloudWatch detects a condition and changes the alarm state. SNS distributes notifications to subscribers such as email endpoints or other integrated systems.

**Q7. Does an ALARM state always mean the EC2 instance has failed?**

No. It means the configured metric crossed the threshold. An application error can occur even when the EC2 instance and its service remain healthy.

## 11. Important operational notes

1. CloudWatch metrics may take time to appear after traffic is generated. Do not expect every request to immediately produce a visible graph point.
2. ALB health checks do not contribute to the ALB request metrics.
3. Use the same resource dimensions when selecting or querying metrics.
4. A missing graph does not automatically mean the application is broken. Check traffic, metric dimensions, time range and period.
5. A CloudWatch alarm evaluates a metric; it does not automatically repair the application.
6. Keep the Terraform configuration aligned with any manual infrastructure changes made during the class.
